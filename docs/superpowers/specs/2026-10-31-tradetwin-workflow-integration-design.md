# TradeTwin AI 双工作流整合设计

## 目标

将用户的工作流一并入主线体验，并以它替换主线中重复的买家变更理解与报价交互；保留队友负责的工作流二，继续作为证据覆盖、补测结论和代价计算的唯一来源。两者围绕同一询盘/案件协作，不复制测试规则、费用或交期计算。

本地整合目标暂定为 `integration/` 中的完整 Node 主线快照。当前 Git 根目录只有项目介绍文档提交，未配置 remote；根目录 `app/` 是工作流一快照，`integration/workflow-1/` 是其副本。因此本阶段只对本地代码做审查与整合，不假设能直接合并或推送 GitHub 分支。不要覆盖、移动或清理这些现有输入。

## 职责边界

### 工作流一：买家变更理解与报价选项

- 接收中文整理、英语/德语原文、后续买家消息或业务员指令。
- 从原文提取结构化变更单；字段需保留原文出处，并区分已确认、未提及、暂定和冲突信息。
- 追问缺失的关键参数；在参数或工作流二核验不完整时，不生成确定的金额和交期。
- 生成候选配置、英德报价草稿、买家追问和发送前风险校验；不自动发送买家消息。
- 维护会话轮次和买家选项选择。买家选择方案与同一消息中的显式参数冲突时，以显式参数为准，并在结果中保留冲突/追问。

### 询盘收集入口

工作流一保留邮箱和浏览器插件两个入口。两个入口使用同一套抽取、变更单、工作流二核验、报价生成和发送前校验，但渠道身份、会话关联及回复回写方式不得混用。

| 入口 | 适用场景 | 获取买家消息 | 回复回写 |
|---|---|---|---|
| 邮箱 | 展会客户、独立站、老客户 | 通过 IMAP 只读拉取；拉取不把邮件标为已读；同一封往来的邮件自动归入同一会话 | 将回复存入邮箱草稿箱，保留正确的回复链头；业务员在邮箱内检查并手动发送 |
| 插件 | 阿里巴巴国际站 IM / RFQ | 读取业务员选中的文字，或在未选择时读取页面最近一段买家消息 | 将回复填入当前页面的回复框；发送按钮始终由业务员手动点击 |

邮箱会话优先使用稳定邮件头（`Message-ID`、`In-Reply-To`、`References`）关联，缺失时才使用受控的主题和参与者回退规则；不得仅凭相同主题合并不同买家。重复拉取同一邮件应幂等。写入草稿时保留原线程所需头部，不自动调用 SMTP 发送。

插件只读取当前允许站点和当前标签页中的必要文本。优先采用用户明确选中的内容；读取“最近一段消息”时必须在界面中展示实际送入分析的原文，允许业务员修改或取消。填入回复框不得触发提交、回车发送或自动点击；找不到可信回复框时停止回填并提供复制操作，不猜测 DOM 目标。

### 工作流二：证据覆盖核验与补测清单

- 以 Node 主线的报告、人工确认状态、规则、费用和周期数据为事实来源。
- 对工作流一提交的每个候选配置，返回逐测试项的覆盖状态、补测/文件更新、人工核验、金额/周期、来源版本和证据页码及原文。
- 不读取工作流一的商业价格表或本地参考引擎作为正式核验结果；工作流一的本地实现仅可用于明确标识的离线演示/测试。
- 证据不足、参数未知或规则无法判断时，金额与周期为未知（`null`），不得以零费用或确定报价替代。

## 架构与接口

保留 Python/FastAPI 与 Node/Express 两个既有服务，通过 Node 同源代理连接；不在本阶段重写任一工作流到另一语言。

- Node 提供主线 UI、案件/证据/知识库/审计存储，以及 `/api/workflow2/envelope` 和 `/api/workflow2/evaluate`。
- Node 代理 Python 销售界面 `/sales/`、静态资源和 `/api/workflow1/*`。Python API 只监听本机，不向浏览器暴露密钥或内部地址。
- 工作流一通过 `tradetwin.wf2.v1` 调用工作流二。请求至少包含版本、唯一 `request_id`、市场/产品范围和 A/B/C 候选配置；响应按 `config_id` 返回可追溯 findings、证据、补测项、费用/周期、人工确认状态及规则/证据版本。
- Node 根据工作流一 `session_id` 同步结构化变更、当前配置、轮次、方案与业务回复到同一案件，并记录来源和审计事件。重复同步同一 `run_id` 必须幂等。
- 方案编号以工作流一的候选配置为准；不复用主线旧方案编号语义。每个报价数字必须能映射到工作流二返回的配置和代价。
- 工作流二适配器校验版本、请求关联、配置 ID、必需字段、金额/周期类型及证据页码。未知状态降级为人工核验；引用缺失的“可沿用”结论不可用于报价。

## 数据流与状态

1. 邮箱或插件把买家原话及渠道元数据送入工作流一；模型/规则提取结果保留原句证据，不确定字段成为追问。邮件线程 ID 或插件会话 ID 映射到稳定的工作流一 `session_id`。
2. 工作流一生成候选配置并调用工作流二批量核验。
3. 工作流二按当前主线证据与规则计算覆盖、补测、文档更新、费用和周期，并返回版本及证据引用。
4. 工作流一将结果组合为英德草稿和内部待办；校验器阻止无依据金额、交期或合规承诺。
5. 工作流一同步完整轮次到 Node 案件；品质人员在主线证据视图复核或补充证据。
6. 证据、规则、费用或确认状态变化后，旧结果不能作为新报价依据；下一轮必须重新请求工作流二并保留旧轮次审计。

## 失败处理与安全边界

- Python 服务或 Node 工作流二不可用、超时、返回畸形数据、版本不匹配或请求关联不匹配时，显示可恢复错误及所需追问/人工待办；不得伪装成成功的本地计算。
- 工作流二失败时不输出确定金额和天数，不将该轮作为可复用的成功幂等结果；服务恢复后允许同一会话重试。
- 外部消息只保存邮箱草稿或填入页面回复框，不自动发送；邮箱读取不改变已读状态，插件不得代替用户点击发送。模型仅用于理解和表达，不决定覆盖结论、补测、费用或周期。
- 邮箱授权码、IMAP/草稿箱凭据和模型密钥仅在服务端配置，不进入浏览器、日志、案件导出或模型上下文。插件权限限制到实际支持的站点和完成读取/回填所需的最小范围。
- 合成报告、映射、客户、费用和周期应持续标记为演示数据；工作流不替代实验室、认证或企业合规负责人的最终判断。

## UI 与兼容性

- 主线保留案件队列、品质核验、证据库、知识库、规则和审计；从案件提供工作流一入口。
- 删除/隐藏主线中重复的买家聊天、报价方案生成与英语/德语回复流程，避免双重状态源；不删除品质人员的证据核验、人工覆盖或审计能力。
- 工作流一结果可从主线跳转到对应案件；品质核验完成后可回到同一工作流一会话继续处理。
- 缺少 Python 依赖或服务未启动时，主线其他功能仍可运行，并给销售工作台显示明确、可恢复的不可用状态。

## 验收

- 邮箱入口能以只读方式拉取消息且不改变已读状态；同一邮件线程稳定映射到一个会话，重复拉取不重复创建轮次；生成结果进入带正确回复链头的草稿箱且不自动发送。
- 插件能优先读取选中文字，并在回退到最近一段消息时展示实际输入；回复只填入阿里巴巴国际站 IM/RFQ 的可信输入框且不触发发送，找不到输入框时安全停止并允许复制。
- 中文整理、英语/德语原询盘及第二轮买家修改均能保留来源片段并生成结构化变更单；缺失参数会追问。
- 36W/IP44 与 30W/IP44 的候选核验结果分别按主线当前合成数据得到 €2,100/8 个工作日与 €900/7 个工作日；若主线证据/规则变更，期望值应随来源更新，而不是硬编码在工作流一。
- 买家选择方案、显式修改配置和暂不承诺交期能重新核验并同步回复/待办；显式参数优先于方案默认配置。
- 缺失证据、未确认范围、未知参数、错误契约、工作流服务不可用时不得生成确定报价；可见人工复核和追问。
- 证据变更会改变证据版本并使下一轮重新计算；同会话轮次同步与重放幂等，不覆盖旧审计记录。
- Node 契约/API 测试、Python 工作流一测试、前端构建，以及本机 Node+Python HTTP 联调通过；结果如实记录。真实模型凭据未配置时不声称完成真实模型验收。

## 方案选择

采用两服务、Node 同源代理、版本化 HTTP 契约。相较于把 Python 业务流重写为 Node/React，它最大限度保留现有实现并降低行为漂移；相较于两个独立界面并列运行，它提供同源入口、共享案件和单一代价来源。
